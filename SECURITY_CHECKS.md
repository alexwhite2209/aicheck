# SECURITY_CHECKS — модуль безопасности (платная проверка)

Методология на основе 12 навыков OWASP (Web App Pentest, XSS, SQLi, Broken Access Control, CORS, Host Header
Injection, Sensitive Data Exposure, Open Redirect, JWT, API Security, BOLA/IDOR, Vulnerability Triage).

## Главный принцип законности

Активная проверка чужого сайта без согласия владельца = неправомерный доступ (ст. 272 УК РФ) и нарушение
ст. 10.1 149-ФЗ. Поэтому проверки разделены на два уровня:

| Уровень | Что делает | На каких сайтах |
|---|---|---|
| **S1 — пассивный** | Анализ того, что сервер отдаёт любому посетителю: заголовки, тело страниц, уже собранный JS, cookies, параметры URL. Отдельные безопасные GET-запросы (CORS, security.txt, типовые адреса утечек) без эксплуатации. | Любой сайт (в платном отчёте) |
| **S2 — активный** | Нагрузочные пробы с тест-нагрузкой (XSS-маркеры, одиночная SQL-кавычка, Host-header, Open Redirect, IDOR с тест-аккаунтами). Только безвредные, неразрушающие, с rate-limit и журналом. | **Только после подтверждения владения доменом** (DNS TXT или файл `/.well-known/norma-verify.txt`) |

S2-пробы в MVP выключены (каркас готов, `SECURITY_ACTIVE_ENABLED=false`). Включаются только для доменов,
прошедших верификацию в кабинете. Capcha сервис не обходит; разрушающие действия (DROP, удаление, захват аккаунта)
запрещены всегда.

## Что сервис НЕ делает (даже на подтверждённом домене)

- не извлекает данные из БД, не изменяет и не удаляет данные;
- не получает доступ к чужим аккаунтам и чужим объектам (IDOR проверяется только на тест-аккаунтах владельца);
- не запускает реальный вредоносный JavaScript — только безвредный маркер для фиксации факта отражения;
- не перебирает пути массово и не проводит брутфорс; список типовых адресов короткий и фиксированный.

## S1 — пассивные проверки (из уже собранных данных и безопасных GET)

| ID | Навык | Что проверяется (пассивно) | Статус при проблеме |
|---|---|---|---|
| `SEC_HEADERS_001` | Pentest | Заголовки защиты: CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, HSTS | FAIL/REVIEW |
| `SEC_COOKIE_FLAGS_002` | Pentest | Флаги cookie: Secure, HttpOnly, SameSite у сессионных/авторизационных cookie | FAIL/REVIEW |
| `SEC_SECRETS_003` | Sensitive Data Exposure | Ключи API, токены, приватные ключи, пароли в HTML/JS; значения маскируются в отчёте | FAIL |
| `SEC_EXPOSURE_004` | Sensitive Data Exposure | Доступность `/.git/`, `/.env`, `/.svn`, бэкапов, `/server-status`, листинга каталогов, source maps | FAIL |
| `SEC_CORS_005` | CORS Misconfiguration | Ответ на запрос с `Origin`: `Access-Control-Allow-Origin: *`/отражение + `Allow-Credentials: true` | FAIL/REVIEW |
| `SEC_SQL_ERRORS_006` | SQL Injection | Утечка SQL-ошибок в теле страниц (сигнатуры СУБД) — признак, не эксплуатация | REVIEW |
| `SEC_REDIRECT_PARAM_007` | Open Redirect | Параметры перенаправления (`?url=`, `?next=`, `?redirect=`, `?return=`) — поверхность риска | REVIEW |
| `SEC_JWT_008` | JWT Security | JWT в cookie/ответах: `alg:none`, слабый алгоритм, отсутствие `exp`, чувствительные данные в payload (только декодирование, без подбора ключа) | FAIL/REVIEW |
| `SEC_SOFTWARE_009` | Pentest | Раскрытие версий ПО/CMS/сервера (Server, X-Powered-By, generator, пути WP/Bitrix) | REVIEW |
| `SEC_MIXED_CONTENT_010` | Pentest | Загрузка ресурсов по HTTP на HTTPS-странице | REVIEW |
| `SEC_API_SURFACE_011` | API Security | Обнаруженные API-эндпоинты (`/api/`, `/graphql`, swagger/openapi); открытая документация API | REVIEW |
| `SEC_ACCESS_HINTS_012` | Broken Access / BOLA / IDOR | Признаки: последовательные ID в URL (`?id=123`), ссылки на админку, на публичной части — только подсказка к ручной проверке | REVIEW |

## S2 — активные пробы (только подтверждённый домен; каркас)

`SEC_XSS_A`, `SEC_SQLI_A`, `SEC_OPEN_REDIRECT_A`, `SEC_HOST_HEADER_A`, `SEC_IDOR_A` — безвредные неразрушающие пробы.
Запускаются по одному мягкому запросу на параметр, фиксируют только признак (отражение маркера, редирект на
тест-домен, SQL-ошибку), без извлечения данных. Требуют: подтверждения домена + явного согласия владельца в кабинете.

## Vulnerability Triage (навык 12)

После всех проверок `triage()`:
- убирает дубликаты и явные ложные срабатывания (например, «секрет», совпавший с публичным ключом reCAPTCHA/Metrika);
- присваивает уровень: `critical` / `high` / `medium` / `low` / `info`;
- связывает находки, затрагивающие персональные данные, с **152-ФЗ ст. 19 ч. 1** (меры защиты ПД) и
  **КоАП ст. 13.11 ч. 6** (нарушение мер защиты, повлёкшее неправомерный доступ) — для сайтов, собирающих ПД;
- формирует общий **Security score** (отдельно от Compliance Score).

Security score и находки безопасности показываются только в платном отчёте и не входят в основной Compliance Score.
Дисклеймер: результаты — информационная проверка, не аудит безопасности по ГОСТ/PCI DSS и не пентест-отчёт.

## Реестры (платная проверка, модуль registries)

| Реестр | Что даёт | Источник | Ограничение |
|---|---|---|---|
| ЕГРЮЛ/ЕГРИП | Компания/ИП по ИНН действует, наименование совпадает | ФНС (egrul.nalog.ru / API ЕГРЮЛ) | капча на веб-форме → нужен официальный доступ/платный API |
| Реестр операторов ПД | Зарегистрирован ли владелец как оператор | pd.rkn.gov.ru | публичный поиск, часто капча → по возможности |
| Реестр провайдеров хостинга | Легальность хостинга (иначе риск блокировки) | rkn.gov.ru | публичный список |
| WHOIS домена | Возраст домена, регистратор, срок | RDAP (rdap.tcinet.ru для .ru/.рф) | публичный |

Реестры: сначала факт с официального источника, потом вывод. Если доступ закрыт капчей — помечаем «требует ручной
проверки» и даём прямую ссылку, а не обходим защиту.
